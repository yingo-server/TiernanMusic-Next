# YKG 协议浏览器链接 · 密码学设计（主会话草稿 · 待 A1-C3 交叉比对后定稿）

> 需求原文（用户 2026-11-16）：
> 「等待方式支持 ykg 协议的浏览器链接，本质是 base64 编码的 cookie 加 md5 加盐密码等信息，
> 支持从 app 导出，输入密码才能通过此方式登录，具体密码学自己设计」
>
> 状态：**设计稿**。本轮审查只出设计不动代码；实现放在阶段 A 七批修完、阶段 B 验证之后。

## 1. 目标与威胁模型

| 目标 | 说明 |
|---|---|
| 导出 | App 把当前登录态（cookie / token / userid / vip）打包成一条**可在浏览器粘贴的文本链接** |
| 导入 | 另一台设备粘贴该链接后，**必须输入导出时设置的密码**才能用；密码错则一律失败 |
| 跨端 | 链接本身自包含（不依赖服务端），两端 App 互导可用 |
| 可识别 | 链接一眼可辨（`ykg://` 前缀），且粘贴时能提示「这是登录凭据链接」 |

**威胁模型**：链接等价于 bearer 凭据，会经由聊天软件/剪贴板/截图流转，可能被中间人看到。
因此设计目标是把「拿到链接」与「能登录」**解耦**：没有密码，链接里的 cookie 在密码学上不可解密。

## 2. 报文结构

链接原文格式：

```
ykg://import/<BASE64URL(UTF8(JSON payload)) 无填充>
```

payload JSON（字段名短，省体积）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `v` | int | 协议版本，固定 `1` |
| `u` | string | userid（明文，便于 UI 显示"这是谁"的账号；不敏感） |
| `s` | string | salt，base64url(16 随机字节) |
| `n` | string | nonce，base64url(12 随机字节)，GCM IV |
| `c` | string | ciphertext，base64url(AES-256-GCM 密文) |
| `t` | string | GCM auth tag，base64url(16 字节) |
| `m` | string | 兼容字段：md5 摘要（见 §4） |
| `ts` | int | 导出时间戳（秒） |
| `exp` | int | 过期时间戳（秒，默认导出后 7 天，可配） |
| `d` | string | 明文 cookie 的**摘要指纹** base64url(md5(cookie))，用于导入后校验完整性（不泄露内容） |

密文 `c` 解密后的明文是 canonical JSON：

```json
{"cookie":"...","token":"...","userid":"...","vip_token":"...","vip_type":"...","dfid":"...","mid":"..."}
```

## 3. 密码学核心

### 3.1 密钥派生（不用裸 MD5 做口令哈希）

```
salt  = 16 字节 CSPRNG（Random.secure）
dk    = PBKDF2-HMAC-SHA256(password, salt, iterations = 120000, dkLen = 32)
```
- `dk` 即 AES-256 密钥。
- 迭代次数 120k：2026 年 ARM 手机上约 0.3–0.8 s，可接受；后续可随设备性能自适应并写入 payload 字段 `it`。
- **算法实现一律调用成熟库，不自研密码学原语**：PBKDF2/HMAC/SHA-256 走 `crypto` 包的标准实现，`Random.secure()` 用 Dart 官方 CSPRNG。我们自己的贡献只是**封装方式**——payload 报文结构、字段语义、aad 绑定串、迭代次数自适应策略、导入/导出流程与层落位。
- 若后续要升级到 Argon2id，通过成熟库（`cryptography`）替换并在 payload 加 `kdf` 字段做版本路由，仍是换库而非自研。

### 3.2 密文（AEAD）

```
ciphertext, tag = AES-256-GCM(dk, nonce, plaintext = canonicalJson, aad = "ykg-v1")
```
- **GCM 而不是 CBC**：自带完整性认证，密文被改动会在解密时直接失败，不存在 padding oracle /  malleability。
- `aad` 固定串 `"ykg-v1"`：把协议版本绑进认证标签，防止跨版本/跨用途复用同一密钥。
- **不用现有的 `AesCbc`（core/net/crypto_aes.dart）**：那个是给酷狗官方协议用的 CBC+PKCS7，不适合自建格式。自建格式改用成熟库提供的 AES-GCM（见 §8），我们只决定参数（256 位密钥、aad 绑定版本、nonce 12 字节）。

### 3.3 导入时的密码门

导入流程（**必须先验密码，再碰密文**）：

1. 解析链接 → 校验 `v`、`exp`、`s`/`n`/`c`/`t` 字段完整 → 立即在 UI 提示「检测到 YKG 登录链接（凭据），导入需要密码」。
2. UI 弹出密码输入（**独立弹层，不自动填、不预填、不缓存**）。
3. 用输入密码派生 `dk'` → 用 `dk'` 解密 `c`：
   - **GCM tag 校验失败** ⇒ 密码错 ⇒ 统一错误文案「密码错误或链接已损坏」，**不区分**（避免 oracle）。
   - 解密成功 ⇒ 再比对明文里的 `d` 指纹与 payload 的 `d` 字段是否一致 ⇒ 不一致说明密文被替换 ⇒ 拒绝。
4. 全部通过 ⇒ 才把 cookie/token 等写入本地凭据存储，并标记来源为 `ykg`。

> 关键点：**密码正确与否由 AEAD tag 校验决定**，payload 里的 `m` 字段只是**快速失败用的兼容摘要**，不能作为唯一判据（见 §4）。

## 4. 关于「md5 加盐」的正确用法（与上游/描述的兼容层）

上游 YKG 生态的链接常见形态是 `md5(salt + password)` 之类的摘要串联。本设计**保留这一层作为兼容字段 `m`**：

```
m = md5Hex( utf8( salt_b64 + ":" + password_utf8 ) )
```
- 用途一：导入端可以先比对 `m`，密码明显不对时**免去一次昂贵 KDF**（快路径）。命中失败即返回错误。
- 用途二：与上游/旧版链接互操作时按同样规则生成 `m`，使旧链接能被新 App 识别。
- **风险与处置**：`md5(salt+password)` 对低熵口令是**弱**的（可离线爆破），所以：
  - `m` **只**用于快速失败与兼容标记，**绝不**作为放行凭据；
  - 真正的放行判据是 GCM tag（`dk` 由 120k 轮 PBKDF2 派生）；
  - 文档与 UI 不得宣称 `m` 是安全校验。
- 因此攻击者即使拿到链接并离线爆破 `m`，拿到的也只是弱摘要，**仍无法解密 cookie**（解密需要真正的 `dk`）。

## 5. 导出流程

1. 用户在「账号/登录」页触发「导出 YKG 链接」。
2. **必须先设置/输入一个导出密码**（不是当前账号密码，是本条链接的保护口令）：
   - 已有导出密码 ⇒ 直接输入验证；
   - 未设置 ⇒ 新设（≥6 位，带强度提示）。
3. App 读取当前 session 凭据 → canonical JSON → AES-256-GCM 加密 → 组 payload → base64url → 拼 `ykg://import/...`。
4. 提供「复制到剪贴板」与「分享」。
5. **强制风险提示文案**（这条是 C3 文案任务的一部分）：
   > 「此链接包含你的登录凭据，任何拿到链接的人若同时知道密码都可登录你的账号。请勿公开分享。」
6. 建议同时显示「有效期至 YYYY-MM-DD」。

## 6. 存储与生命周期

| 项 | 方案 |
|---|---|
| 导出密码 | **不存明文**。存 `verifier = PBKDF2(password, storedSalt, iters, 32)` 的一个对比值（用不同 salt 二次派生），用于「重新导出时验证密码」 |
| 链接本体 | 默认**不落盘**，只在内存/剪贴板；用户若要存档才写文件，并置于 `app_flutter` 私有目录 |
| 剪贴板 | 导出后写剪贴板；**建议 60 秒后自动清空**（仅当剪贴板内容仍等于本链接时才清，防覆盖用户后来复制的内容） |
| 过期 | payload `exp` 到期 → 导入端拒绝；已导入的凭据不受影响 |
| 撤销 | 酷狗侧改密码/登出后链接失效；本地可「吊销本机已导入的 YKG 凭据」 |

| 关注点 | 归属层 | 说明 |

| 新增依赖 | `pubspec.yaml` + `tool/layer_audit.py` + `tool/smoke_check.dart` 白名单 | CI 门禁会拦越层与未登记依赖 |

## 8. 依赖方案（算法用成熟库，封装自己设计）

**原则**：所有密码学原语（PBKDF2 / HMAC / SHA-256 / AES-GCM）**一律调用成熟库**；我们自研的只有「封装层」——报文结构、字段编码、aad/nonce 约定、导入导出流程、层落位。

- **方案 1（推荐）**：新增 `cryptography: ^2.x`（成熟库，纯 Dart + 平台优化双实现）→ 一次拿到标准 `Pbkdf2`、`AesGcm`、`Random.secure`，自家代码只做「拼 payload / 加 aad / 走流程」，约 100 行封装。
  - 优点：算法经过审计，不自己写一行密码学；GCM 的 nonce/tag 处理由库保证正确。
- **方案 2**：`crypto: ^3.x`（`sha256`/`hmac`） + `encrypt: ^5.x`（`AES-GCM` 封装）→ 两个流行成熟库组合，PBKDF2 用 `crypto` 的 `Pbkdf2` 标准类（仍非自研）。
- **不选**「全自研 SHA-256/HMAC/PBKDF2/GCM」：用户明确要求算法用成熟库，手写 GCM 风险最高，直接排除。
- 现有的自研 `Md5`（`core/net/signing.dart`）**继续只服务酷狗官方协议签名**；YKG 兼容字段 `m` 也调这个成熟实现，不新增 md5 自研代码。
- 依赖登记：`pubspec.yaml` + `tool/layer_audit.py` + `tool/smoke_check.dart` 白名单同步。
- 实现后必须补离线回归（`tool/` 下新增契约测试），覆盖：往返加解密、错误密码必失败、篡改密文必失败、错 salt/错 nonce 必失败、过期链接被拒。

## 9. 待定项（等 A1-C3 交叉比对后定）

1. `it`（迭代次数）是否写入 payload 以支持自适应升级（倾向写）。
2. `exp` 默认 7 天是否合适（用户可能想要永久链接）——产品决策。
3. 导出密码是否复用账号密码（**倾向不复用**：账号密码是服务端凭据，本地保护口令应独立）。
4. 是否需要「多链接并存 / 命名 / 单链接吊销」列表（App 侧凭据管理页）。
5. 链接是否需要二维码形式（`core/algorithms/qr_codec.dart` 已有 QR 编码，可复用）——**倾向要**，扫码导入体验最好。
