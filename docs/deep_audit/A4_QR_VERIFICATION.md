# A4 · QR off-by-one 复核裁定（主会话，2026-11-16）

> 背景：A4-C2 报 P1「qr_codec.dart:283 数据放置列对从 size-2 起 off-by-one，V1–V4 全错、末尾码字丢失、QR 大概率不可扫」。主会话用 Python 精确仿真列对覆盖验证（`docs/deep_audit/verify_qr.py`，本仓库字段真值用 Nayuki 标准 QR 布局对照）。

## 验证结果

```
[V1 size=21] 数据格总数=208  仓库(size-2)覆盖=192  标准(size-1)覆盖=208
   仓库比标准少=16 格, 漏列=[7, 20]
   V1-L 需152bits, 仓库容量192 -> 够放
[V2 size=25] 少24格 漏列[7,24]，容量335≥272 -> 够放
[V3 size=29] 少32格 漏列[7,28]，容量535≥440 -> 够放
[V4 size=33] 少40格 漏列[7,32]，容量767≥640 -> 够放
标准覆盖 == 全部数据格（各版本均 True）
```

## 裁定

- ✅ **真 bug（结构）**：仓库从 `right=size-2` 起配对，标准应从 `size-1` 起。结果：
  - 漏掉最右列（20/24/28/32）与列 7 的数据格；
  - 列对相位整体偏移一列，数据、格式副本、掩码映射与标准 QR **完全错位** → 标准扫码器（微信/系统相机/ZXing）**读不出或读错**。
  - 与代码紧邻注释「标准列对…8/7,5/4,3/2,1/0」自相矛盾（注释说有 8/7，实际从 size-2 起只能到 9/8）。
- ❌ **子代理后果描述有误**：它称「bitIdx 到不了 totalBits、末尾码字丢失」——仿真显示仓库容量 192 ≥ V1-L 的 152 bits，码字**能写完**，不会丢。真实后果是**布局错位导致标准扫码器无法解码**，而非码字丢失。（结构 bug 依然成立，定级 P1 不变。）

## 修复方向（阶段 A 全审完后主会话亲修）

1. 起点改 `right = size - 1`，与 Nayuki 标准对齐（一列之差，改一行）。
2. 补已知 QR 向量离线回归（Nayuki V1-L/M 矩阵逐格对照），堵住测试盲区。
3. 掩码固定 0、无最优掩码属非标准最佳实践（C2 已指出），但能解码；若接入 YKG 扫码，按用户「成熟库」原则优先换 `qr` 包，自研实现退役或仅留兼容。
4. 当前 `encodeQr/QrMatrix` 全仓零业务调用（死代码，YKG 扫码未接线），故此 bug **暂不影响现有用户**，但 YKG 落地前必须修。

## 对汇总的影响

A4-C2 的 QR 条保留为 P1，后果描述按本复核修正。又一个「子代理静态发现 + 主会话仿真复核（确认 bug、修正后果）」的质量 gate 实例。
