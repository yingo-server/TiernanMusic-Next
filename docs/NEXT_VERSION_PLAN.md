## 1. 结论摘要（三条，均为 P0）

1. **UI 不合格**：新版只有"骨架能跑"，信息密度、内容层级、交互路径全面落后旧版。旧版 8 张截图里每个屏都有 3–5 个内容区块 + 明确的操作入口；新版首页 2/3 的卡片**没有 onTap**（榜单卡、推荐歌单卡），搜索页丢了"搜索历史 + 热门分类筛选"，音乐库丢了"账号卡 + 我的歌单"。
2. **API 只有锚点，没有契约**：现有 `field_truth_test.dart`（163 断言）验证的是"字段能取到"，**没有**逐端点的三态（匿名/非VIP/VIP）响应样本、字段字典、成功语义矩阵、延迟基准、URL 解析结果、预读/缓存命中数据。用户要的六项证据全部缺失。
3. **发布状态误导用户**：23 个 Release 中 **4 个被标为正式版**（v26.11.13.03/.04/.05/.06），其余 19 个已是 pre。按"目前全部版本主要功能不可用"的判断，这 4 个正式标记必须撤销。

## 5. API 契约矩阵设计（WP3 细化）

### 5.1 矩阵行 = 端点 × 三态

26 个端点模块，每个至少 3 行（匿名 / 非VIP / VIP），写操作另加"成功/风控/未登录"三行。

| 列 | 内容 |
|---|---|
| endpoint | 模块名 + 函数 + HTTP 方法 + 真实 URL/域名 |
| state | anonymous / nonvip / vip |
| http | 状态码、耗时 ms、响应字节数 |
| envelope | 顶层键集合（如 `status/error_code/data/ssaCode`） |
| success | 实测成功判定式（`status==1 && priv_status==1`、`status==200`、`err_code==0`…） |
| fields | 字段路径 → 类型 → 可空 → 出现条件（例：`data.lists[].FileHash`） |
| diff | 与另一态的差异（字段多/少、值不同） |
| verdict | OK / NO_PRIV / NEED_VERIFY / EMPTY / RISK |

### 5.2 必测字段（按已知坑）

- 播放：`status`、`priv_status`、`url`、`backupUrl`、`bitRate`、`extName`、`tracker_through.musicpack_advance`、`IsFreePart`、`end_byte`、`timeLength`
- 搜索：`data.lists[].FileHash/FileName/SingerName/MixSongID/AlbumAudioId`（不是 `data.info[]`）
- 评论：`FileHash` 计数、`like.count`、`tid` 楼层键、`err_code`
- 收藏：`listid=2`「我喜欢」、`data.list[].count`、`/v4/delete_songs` 的 `fileid`
- 歌词：`status=200` + `errcode=200`、`candidates[]` 顶层、KRC `krc1` 魔数
- 用户：`data` 平铺 `pic/vip_type`、裸 RSA 右补零
- FM：`data.song_list[]`、`kuguid=userid`、毫秒 clienttime

### 5.3 延迟采集

- 每端点每态重复 5 次，记录 p50/p95/max；区分冷启动首请求与热缓存命中。
- 单端点超时阈值（默认 8s）+ 重试上限 2 次；记录超时率。
- 输出 `docs/API_LATENCY.md` + CSV，便于回归对比。

### 5.4 凭据与安全

- 使用 `.test_creds/cj_vip.txt` / `cj_nonvip.txt`；匿名 = 无 cookie。
- **不落库、不进仓库**：探针脚本从环境变量/本地文件读取，日志脱敏 token/userid。
- 写操作（收藏/歌单增删/上报）只用测试数据并回滚，禁止触碰真实用户歌单。

## 6. 网络机制设计（WP4 细化）

### 6.1 URL 解析链路（对标旧版 `kg_play_api.dart` 532 行，只读参照）

```
SongBrief + quality
  → 选择音质档（VIP 档降级规则）
  → /v5/url（含 signKey、token/userid、dfid/mid/uuid）
  → 解析：status/priv_status/url/backupUrl/bitRate/extName/
          tracker_through.musicpack_advance/IsFreePart/end_byte/timeLength
  → 判定：OK / NO_PRIV（priv_status=0）/ NEED_VERIFY（20028）/ NOT_FOUND
  → URL 健康检查（HEAD 200/206，超时 3s）
  → 主链失败 → backupUrl 顺序重试（最多 2 条）
  → 仍失败 → 降级档位重试（320→128）
  → 缓存结果（带 TTL，URL 通常短时效）
```

必须回答并写进文档：URL 有效期、是否需要 Referer/UA/Cookie、CDN 域名分布、断链率、试听截断（`end_byte`）与 `IsFreePart` 的真实行为。

### 6.2 三级缓存

| 层 | 内容 | 容量/策略 | 指标 |
|---|---|---|---|
| L1 内存 | JSON 响应（LRU） | 现有 `LruCache`，按 `ns+userid` 失效 | 命中率、evict 次数 |
| L2 磁盘 | 请求 JSON、封面图 | 上限 200MB，LRU + 7 天 TTL | 命中率、占用、清理耗时 |
| L3 媒体 | 播放 URL 文件、歌词文件 | 仅"完整播放完成"后永久缓存 | 复用率、节省流量 |

关键：**同一请求 in-flight 合并**（旧版 `ResourceCache` 有），避免并发重复请求；缓存键 = path + 排序 query + userid。

### 6.3 预读引擎（对标旧版 `PrefetchEngine` 235 行）

- 启动预热：首页可见歌曲（上限 60 首），100ms 间隔，只预请求 URL/歌词/封面 JSON，不下载媒体。
- 队列补充：当前曲后 15 首（`updateUpcoming`），切歌/换队列重入安全。
- 去重：LRU 上限 512；播放完成才 `cacheUrlFile` 永久缓存。
- 上限与退避：队列有界、失败不重试、`dispose` 后回调先查存活。
- 指标：预热命中率、首播耗时（预热 vs 未预热）。

### 6.4 网络阶段可见（对标旧版 `NetworkPhase`）

- 枚举 `idle / resolving / buffering`，深度计数支持并发；>500ms 才显示 UI 指示器。
- UI：MiniBar/播放页显示"解析中/缓冲中"，避免用户以为卡死。

## 7. UI 重构方案（WP5 细化）

- 圆角：卡片 16–20dp；大封面 28dp；胶囊按钮全圆。
- 标题层级：页面标题 34–36sp 粗体；区块标题 22–24sp；条目标题 17–18sp；辅助 13–14sp。
- 间距：页面左右 20dp；区块间 32dp；卡片间 12–16dp。
- 触控：最小 48dp；MiniBar 高 64dp；底部导航 72dp。

### 7.2 逐屏规格

**首页**
1. 顶部横滑 banner（2 张可见，1.7 露出）→ 点击进歌单/活动。
2. 每日推荐横滑卡（封面 96dp + 标题/歌手两行）→ 点击播放；长按/⋮ 入队。

4. 排行榜渐变大卡（TOP500 橙红、星曜绿）→ 点击进榜单详情。
5. 新歌推荐纵向列表（封面/歌名/歌手/时长/⋮ 菜单）→ 点击播放，⋮ 打开"下一首播放/加入歌单/收藏/下载"。

**搜索**
